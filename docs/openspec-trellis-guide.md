# OpenSpec 和 Trellis 怎样配合，让 Agent 真正用上项目规范

这份文档先解释机制，再说明我们准备改哪里。你不需要先了解 OpenSpec 的目录格式、
hook 配置或 Agent 内部实现。

我们要解决的问题是：**你已经写了工程规范，怎样让 Agent 在开发和检查时实际看到它，
并有办法发现漏读和违规？**

文中的后端和页面任务都是讲解示例，不代表这些功能已经实施。稳定版入口现已接入，
实际范围和仍未验收的内容见第 12 节；配置说明不代表模型已经遵守全部规则。

## 1. 先看一次任务实际是怎么发生的

假设你告诉 Codex：

> 帮我调整这个后端接口，要求符合项目的后端规范。

模型并不会因为项目目录里有 `.trellis/spec/backend/`，就自动知道里面所有内容。
它需要先取得这些文件的正文。最直接的过程是：

```text
你提出需求
    ↓
Agent 决定读取适用规范
    ↓
读取工具打开文件，把正文返回给 Agent
    ↓
下一次模型处理时，输入里包含了这些正文
    ↓
Agent 据此分析和修改代码
```

例如，读取工具打开[后端接口规范](../.trellis/spec/backend/api-contracts.md)，
返回其中的规则和例子。这些文字才成为当前上下文的一部分。

这里有三个不同状态：

| 状态 | 实际含义 |
|---|---|
| 文件在磁盘上 | Agent 可以尝试读取，但还不一定看过 |
| Agent 知道文件路径 | 知道去哪里找，仍不等于看过正文 |
| 正文出现在模型输入或读取工具返回中 | 这次执行向 Agent 提供了这些内容 |

**所以，“规范存在”和“规范已进入上下文”之间，必须有一个实际读取或注入步骤。**

## 2. 我们说的 harness 包含什么

这里的 harness 是模型周围帮助它完成任务的一整套东西：

```text
你的请求
  + 项目入口指令
  + 本次需求和验收标准
  + 适用工程规范
  + 文件读取、代码编辑等工具
  + 工作流程
  + 测试和检查结果
```

模型负责理解、判断和生成内容。Codex 等宿主负责组织消息、调用工具、运行 hook。
OpenSpec 和 Trellis 给这套过程提供文件、指令和执行方法。

我们这次主要调整的是项目上下文、工作入口、读取步骤和检查方法，不需要修改模型核心。

## 3. OpenSpec 和 Trellis 分别解决什么

可以直接从一个任务会遇到的两个问题理解：

- **本次究竟要做什么，完成后应该怎样？**由 OpenSpec 保存。
- **在这个项目里，应按什么工程方式做？**由项目工程规范说明，Trellis 帮助组织和提供它们。

| 问题 | 主要由谁负责 | 例子 |
|---|---|---|
| 这次需求是什么 | OpenSpec | 哪些用户可以操作，成功和失败应如何表现 |
| 怎么拆任务、有哪些设计取舍 | OpenSpec | 修改哪些行为，按什么顺序实施 |
| 项目有哪些长期约定 | Trellis 规范目录 | 后端分层、API 错误、前端状态管理、组件规范 |
| 怎样让执行者获得这些约定 | Trellis 读取步骤、可选 hook，以及宿主读取工具 | 选出适用文件，读取或注入正文 |
| 谁实际修改代码 | Agent | 在 OpenSpec apply 阶段实施 |
| 怎样判断做对了 | OpenSpec 验收 + 工程审查 + 测试 | 行为是否符合需求，代码是否符合规范 |

因此，我们保留 OpenSpec 的主流程：

```text
规划需求 → apply 实施 → verify 验证 → archive 归档
              ↑              ↑
        接入工程规范读取  再次核对相同规范
```

Trellis 不需要再为同一个 OpenSpec 变更复制一套需求、设计和正式任务列表。
它可以引用 OpenSpec 原文，保留必要的上下文清单和本地接续记录。

### 你需要手动启动这些步骤吗

日常只需描述需求，不必手工触发同步或输入 Skill 名称。本机启动检查和 Agent 的执行入口
负责准备工具、选择流程并读取规范；若启动自动化不可用，Agent 应自行检查、补读并报告
缺口，不能把执行命令的责任默认交给使用者。

需求分析存在实质歧义时，Agent 主动使用已安装的 `grill-with-docs`，组合 `grilling`
与 `domain-modeling`：先核对能查到的项目事实，再询问会改变业务、边界和设计的决定。
需求明确的小修跳过访谈；已确认答案复用，不重新问一遍。OpenSpec 仍保存正式需求和
设计，澄清不会额外复制一套正式规划。

本机该 Skill 已允许 Codex 隐式选用，工具不存在时直接读取两个组成 Skill 的说明。
自动选择流程不等于代替你做业务决定，必要的澄清问题仍需要你回答。

## 4. AGENTS.md、规范、Skill、hook 之间是什么关系

这几个名字经常一起出现，但作用不同。

| 名称 | 它是什么 | 它不会自动做到什么 |
|---|---|---|
| `AGENTS.md` | 项目入口指令，告诉 Agent 核心规则和去哪里找详细规范 | 不会自动展开所有文档链接 |
| `.trellis/spec/` | 项目的工程规范正文 | 目录存在不代表模型知道里面的内容 |
| Skill | 一份教 Agent 如何执行某类任务的说明 | 不是每条规则都有程序强制执行 |
| hook | 宿主在特定事件发生时运行的脚本 | 配置存在不代表当前会话实际运行了它 |
| 测试、lint、CI | 执行具体检查的程序 | 只能验证已经表达成检查的要求及其覆盖范围 |

举例来说，`trellis-before-dev` 告诉 Agent：开发前从索引选择并读取适用规范。
真正把正文送进上下文的，是随后发生的文件读取，或者宿主执行的正文注入。

此前提到的 `trellis workflow --list` 列出的是整套 Trellis 流程模板，不是 Skill 清单，
也不会启动开发。对于本次方案，主流程由 OpenSpec 承担，我们只在相应环节接入 Trellis
的规范读取和检查方法，不再让同一个需求重复走两遍完整流程。

### 为什么此前讨论 override

Codex 在同一个目录中会优先选择非空的 `AGENTS.override.md`，而不是同时自动加载
`AGENTS.md`。我们用实际 CLI 做过对照测试：两个文件同时存在时，普通 AGENTS 的标记
没有进入自动构建的提示；移走 override 后，该标记出现。

此前 override 里写着“再读 AGENTS.md”，这仍然可以让 Agent 取得正文，但需要后续
真的执行一次读取。当前 worktree 已把该说明保留到 `.trellis/local-workflow.md`，
让项目 AGENTS 正文恢复默认发现；没有批量迁移其他 worktree。

这个测试证明了加载顺序，不等于证明此前所有开发任务都没读规范。
显式文件读取和你直接提供的指令，也能把规范带入上下文。

## 5. 两条正文传递路径：主动读取和自动注入

### 路径一：Agent 主动读取

这是最容易观察，也不依赖 hook 的路径。

```text
OpenSpec apply 或 verify 开始
    ↓
读取项目入口和规范索引
    ↓
根据任务选择具体专题
    ↓
读取专题正文，处理缺失和截断
    ↓
实施或检查
```

优点是跨工具容易使用。薄弱点是 Agent 可能选漏或没有执行读取，所以实施和检查入口都
需要明确要求读取，并核对实际工具返回，不能只看 Agent 说“我已经遵守规范”。

### 路径二：宿主通过 hook 注入

以已有 Trellis 子 Agent 注入为例：

```text
主会话启动一个 Trellis 实现 Agent
    ↓
Codex 触发 SubagentStart
    ↓
hook 找到父会话对应任务
    ↓
读取 implement.jsonl 中列出的文件正文
    ↓
hook 把正文放进 additionalContext 返回
    ↓
Codex 把正文加入子 Agent 的上下文
```

`additionalContext` 只是 hook 返回给宿主的一个字段名，意思是“请把这段文字追加给模型”。
脚本自己打印成功还不够，宿主必须真的触发它、接受输出，并把内容交给相应 Agent。

如果 hook 没加载、没信任、父任务找错、正文太长，自动路径就可能不完整。
这时应明确补读，不能凭“注入标记存在”认定内容齐全。

## 6. 一个后端任务，从需求到验证怎么走

假设已经确认了一个接口的权限行为调整。以下只是流程示例，不是在规定项目的新权限政策。

### 第一步：OpenSpec 说明预期行为

需求需要说明哪些身份可以调用、哪些应该被拒绝、返回什么结果，以及拒绝时能否产生写入。
设计说明实现取舍，任务列表拆分实施和相应验证。

这些内容解决“本次要做什么”。仅写“遵循后端规范”，无法替代具体的业务验收。

### 第二步：apply 先取得本次需求和工程规范

Agent 通过 OpenSpec 获取本次产物位置，再读取原文。同时从
[规范总索引](../.trellis/spec/index.md)选择[后端入口](../.trellis/spec/backend/index.md)，
根据实际影响追加接口、权限相关契约、事务、错误处理等专题。

此时模型应当同时看到两类内容：

```text
本次需求：操作在什么条件下允许、拒绝，结果是什么
工程约定：身份怎样传递、各层职责是什么、错误和事务怎样处理
```

模型随后读取现有代码和测试，按这些依据实施。
Trellis 不需要再复制一份同样的需求文档。

### 第三步：verify 同时检查需求和工程约定

验证至少要看：

- 允许与拒绝分支是否符合本次需求。
- 身份和权限是否使用项目已有机制。
- 被拒绝时是否产生了不应有的持久化变化。
- 相关测试是否实际执行，通过结果对应哪段代码。

任务列表全部勾选，只说明有人记录完成；这些检查才帮助判断需求是否落实。

发现问题后回到 apply 修复，再验证。OpenSpec verify 保持报告式检查，不默认暗中修改产品代码。

## 7. 一个页面任务，设计系统如何真正参与

假设你要求“按照设计系统调整技能列表页面”。

OpenSpec 说明本次页面范围和行为，例如哪些布局要变、筛选行为如何保持、需要覆盖哪些状态。
工程与设计上下文则提供实际实施依据：

| 资料 | Agent 需要从中取得什么 |
|---|---|
| 前端规范 | 状态管理、请求、翻译、组件复用等约定 |
| 主题来源 | 实际颜色、字体、尺寸、间距、圆角等值 |
| 组件契约 | 这次使用的按钮、选择器、弹窗等组件的能力和状态要求 |
| 页面规范 | 页面组合、加载、空态、错误、响应式与键盘行为 |
| 当前源码 | 已有组件和业务能力，哪些能复用，哪些确实需要改 |

只读一篇“我们有设计系统”的说明，不能取得这些具体约束。

当前工作区已有设计库读取工具，例如：

```bash
python3 scripts/read-design-system.py check
python3 scripts/read-design-system.py theme control
python3 scripts/read-design-system.py component button
```

工具读取选定资料，输出正文及来源哈希。哈希帮助确认采用的是哪份内容，不能替代正文。
视觉任务默认采用选定的 SkillHub 设计系统。工具先校验源 CSS 与投影各分组、来源哈希，漂移或缺项会失败；Agent 根据 CSS 刷新派生 JSON，不改权威 CSS 来迎合旧 JSON。正文默认小分页；续页必须带 nextOffset 和 --expect-sha256。不能合并多个大结果。恢复时按[有界读取与接续](../.trellis/spec/workflow/context-reading.md)补读；有日志时工具可检查真实返回中的完整正文，缺段不通过，不依赖记忆自述。

设计库优先取项目本地目录。本机已登记获准资源时，可使用经过完整性校验的私有快照；新 worktree 无需重复复制整包，也不继承其他任务。登记和同步由 Agent 处理。新克隆且没有资源时仍明确报缺失，不应自行填值并声称符合设计系统。

实施后，还要实际检查明暗主题、长文本、窄屏、焦点、弹层和完成状态。
“类型检查通过”和“页面符合设计要求”是两个不同结果。

Figma 是可选的画板和证据渠道，默认不启用。明确选择时使用 `figma-web-bridge`；
不需要为了让规范有效，先强制把所有任务放到 Figma。

## 8. OpenSpec 怎样接入这些读取步骤

OpenSpec 原生入口会调用终端 CLI 取得当前任务信息，例如：

```bash
openspec status --change <change-id> --json
openspec instructions apply --change <change-id> --json
```

`<change-id>` 是实际变更名。返回结果包含产物路径、任务、当前可执行状态，以及配置了以后
的项目上下文。Agent 还要读取返回路径对应的文件，CLI 不会自动读取所有外部规范链接。

稳定版已通过 `openspec/config.yaml` 接入读取要求。下面是简化示意，完整配置以文件为准：

```yaml
schema: spec-driven

context: |
  实施和验证前，读取 AGENTS.md 与 .trellis/spec/index.md。
  选择并读取本任务适用的工程规范正文。
  页面任务还需读取实际使用的主题和组件契约。

operations:
  apply:
    guidance:
      - 可使用已安装的 trellis-before-dev 完成读取；不可用时显式读取。
```

我们已经用真实 CLI 验证：这里的 `context` 和 apply 指导会进入原生指令输出。
也验证了：里面的文件路径不会自动展开为正文。因此接入包括两步：

1. 把读取要求放进 OpenSpec 能提供给 Agent 的原生指令。
2. 在执行过程中检查 Agent 是否真的读取了选中的正文，缺失或截断就补读。

`rules.tasks` 是生成任务文档时的规则，不是实施阶段的规范正文入口。
当前版本也没有 `operations.verify`；验证入口需要明确接上项目规范读取，不能假定
apply 的指导自动成为 verify 的动作。

还有一个细节：当前 `trellis-check` 包含修复机械问题的步骤，而 OpenSpec verify 是报告式
验证。因此我们要复用其规范检查与选测方法，不能把会自动修复的整套动作直接塞进 verify。

## 9. 新版 Trellis 的路径注入补充了什么

稳定版已有按任务清单向指定子 Agent 提供正文的机制。我们还检查了
`0.7.0-beta.4` 的路径注入能力，它更接近“准备改哪里，就补充哪里的规范”。

例如，规范可以声明适用路径：

```markdown
---
paths:
  - server/**
---
这里是适用于这些后端路径的规范正文。
```

在支持的结构化编辑路径中，hook 能匹配待修改文件。隔离测试中观察到的过程是：

```text
Agent 第一次尝试修改匹配文件
    ↓
hook 返回适用规范全文及拒绝本次修改的结果
    ↓
宿主若正确处理该结果，Agent 先看到规范，再重试修改
```

这比单纯提醒 Agent 更接近运行时约束，但当前还不能说已经保障了我们的真实会话：

- 测试版尚未正式安装启用，宿主是否触发、是否执行拒绝仍要实测。
- 当前规范还没有配置这些路径，升级本身不会自动完成适用范围标注。
- 该路径 hook 不覆盖所有 Shell 写入，也不能替代只读验证阶段的规范读取。
- 路径匹配不知道全部业务含义；跨层影响仍要根据需求和实际代码判断。

因此它是可选增强。基础流程先用原生入口和显式读取接通，再决定是否采用这项能力。

## 10. 怎样知道规范有效，而不是听 Agent 保证

需要分别核查下面三件事：

| 要核查的事 | 有用的证据 | 单独不够的证据 |
|---|---|---|
| 来源选对了 | 需求、影响范围与选中专题的对应关系 | 只说“读了后端规范” |
| 正文送达了 | 实际模型输入或读取工具返回中有对应正文，截断已补齐 | 文件存在、路径、注入标记、哈希 |
| 实现符合要求 | 对照源码的评审、实际测试和必要的页面/业务验证 | Agent 宣称遵守、任务全勾选、构建通过 |

作为使用者，你不必每次阅读全部底层记录，但任务交付应该能回答：

> 这次使用了哪些工程规范和设计来源？必需正文是否完整取得？
> 做了哪些验证？哪里发现过问题？哪些环境或场景还没有验证？

对于能自动判断的规则，尽量用测试、lint、检查脚本或 CI 检出违规。
架构取舍和视觉质量仍需相应评审。不能因为有 hook，就声称所有规则都有强制保障。

## 11. 为什么换会话、压缩上下文后还要检查

磁盘上的文档会一直存在，但当前模型能看到的消息有容量限制。新会话不会天然拥有上一会话
读过的所有正文；上下文压缩后的摘要，也未必保留完整组件契约或工程规则。

恢复时不需要重读整个仓库，而是重新确认：

1. 当前使用哪个 OpenSpec 变更，任务与需求有没有改。
2. 本次适用哪些规范，来源是否变化。
3. 当前上下文是否还有必需正文；没有就重新取得。
4. 哪些已有检查仍适用，哪些因代码或契约变化需要重跑。

子 Agent 也一样：不能只因为主会话读过，就假定它已经继承了全部正文。

| 使用效果 | 两个隔离 worktree 的受控页面审查已验证；真实后端和页面实施、浏览器验收仍待验证 |

稳定版现在可以这样使用：

```bash
python3 scripts/setup-agent-workflow.py          # 查看本项目入口的生成计划
python3 scripts/setup-agent-workflow.py --apply  # 需要安装或恢复适配时执行
python3 scripts/setup-agent-workflow.py --check  # 检查入口是否缺失或被更新覆盖
```

这些命令使用已安装的 OpenSpec 1.17.0，在临时配置中调用官方生成器，不修改你的全局 profile。
生成入口保存在本地 `.agents/skills/`，检查元数据在被忽略的 `.dev/` 中。自定义冲突会停止，
不会强行覆盖。普通 `openspec update` 可能覆盖适配或移除可选 verify，之后需重新运行上述检查。

在 Codex 中使用生成的 `openspec-propose`、`openspec-apply-change`、`openspec-verify-change`
等入口；如果当前界面还没刷新技能列表，重新加载工作区或新建对话后核对。当前会话也可以
显式读取对应 Skill 和项目规范执行，不把菜单可见性当成正文送达证明。

### 换 worktree 和新对话的实测边界

本次用两个独立 worktree、三个全新 CLI 会话验证同一类候选组件；其中一个会话只收到
普通中文审查请求，未点名 Skill。它自行选择了原生 verify。审查者能够取得本 worktree
的正式产物、适用规范与实际组件正文，指出不支持的按钮尺寸、取数和国际化问题；缺少
私人设计库的 worktree 则明确保留设计一致性未验证。候选代码及正式任务清单保持原样。
这些是受控静态审查结果，不是产品实现、类型检查或浏览器验收。

还在原 worktree 创建了原生新对话：入口检查通过，宿主列出两个可信启用的 Trellis hooks；
原旧线程仍缺少它们。没有取得实际 hook 正文自动投递证据，不能仅凭列表宣称投递修复。

新 worktree 只包含所选 Git 基线，**不会继承另一 worktree 的未提交改造、私人设计库或
已读上下文**。本次明确复制了待提交的共享改造并运行安装工具，才开始新会话验证；不是
直接从远端干净克隆就已具备全部改造。实际采用时先确认分支包含改造，再执行上述安装与检查。
首轮实测还发现本机模板缺少新增的 OpenSpec 优先路由。该分发问题现已沿用原有
publish/sync/SessionStart 修复：已选择性发布工具改动，文件版本记录能检出旧版，
未定制的旧文件备份后更新，未知定制保留并报告冲突；配置中的工作区个人选择保留。
两个测试 worktree 已升级，且规范、候选源码和正式任务清单保持不变。

本机已安装这些可选工具时，可从目标工作区执行：

```bash
skillhub-trellis-local-sync --check  # 只检查工具文件及本分支已有的 OpenSpec 入口
skillhub-trellis-local-sync          # 补齐或安全更新；衔接已有 OpenSpec setup/check
```

`wt-new` 仍调用同一个同步入口；SessionStart 现在检查内容版本，不再仅凭文件存在跳过。
设计 Skill 和读取工具也复用该入口补齐；旧分支没有共享读取脚本时使用本地回退工具。
设计资源只登记到用户私有缓存并校验，不进入 Git，不覆盖分支规范。
只有需要把已审阅的工具变更带回本机模板时，才显式执行
`skillhub-trellis-local-publish --tooling-only`；该模式不发布规范。原有不带该参数的发布
仍包含规范，应先审阅。默认同步保护分支已跟踪规范，不复制任务、会话和运行状态，也不
创建遮挡项目入口的 override。同步不安装依赖、不修改 hook 信任；并发同步按工作区加锁。

这些是本机可选自动化，不是开源使用者必须具备的私人命令。若分支还没有共享的
`setup-agent-workflow.py`，同步会提示 OpenSpec 集成跳过，不能据此宣称该分支已装好完整入口；
应切换到含已审阅改造的分支，继续使用前文公开的 setup/check。

后续仍需完成真实使用验收：

1. **实施：**核对真实 apply 是否先取得需求、适用工程规范和设计正文。
2. **验证：**核对真实 verify 是否读取同组依据，保持报告式检查，问题回到 apply。
3. **恢复：**在新会话、压缩和资料变化后核对必要正文是否重新取得。
4. **实际验收：**用后续已授权的真实前后端任务证明链路和对应行为；不为试点擅自新增产品需求。

安装工具 setup/check 只负责调用官方生成器、保留读取适配
并检查生成文件是否漂移；它不选择业务规范、不替 Agent 读取正文，也不改变 OpenSpec 任务状态。

这份文档用于阅读和理解，不另设正式要求。后续需要逐项审阅改动时，再看
[详细实施方案](../openspec/changes/harden-agent-spec-context/design.md)及其任务、验收规范。

## 13. 正文读取与恢复的补充验收（2026-11-11）

前一节保留首轮接入记录；本节说明后续已补齐的范围。现在除了入口安装，还提供独立的正文读取和送达检查：

1. Agent 根据任务选择规范，使用 `scripts/read-context.py file PATH` 一页一页取得正文。设计资料通过 `scripts/read-design-system.py` 读取完整选中契约。
2. 每页包含正文、来源摘要和下一页位置；续页必须固定同一份内容。它解决工具输出过大被截断的问题，不把规范改成摘要。
3. `scripts/read-context.py check` 对照当前会话的实际工具返回，检查选中资料有没有缺页、过期或仅在压缩前出现。专题声明的必需关联也会加入检查；选哪些专题仍需要 Agent 判断。
4. 新对话、压缩或资料变化后重新取得当前必需正文。旧的“检查通过”只属于当时的上下文，不能作为现在已读的证明。

两个独立新对话中已观察到精简启动提示的真实投递。首轮审查遗漏的专题被保留为失败，补充必需关联后，选中的14项工程与设计正文完整取得。在原界面执行真实压缩后，检查先拒绝压缩前的旧正文；继续任务并补读后，14项重新通过。范围限于该只读案例，不证明所有任务都自动选对规范，也不证明业务代码一定遵循规范。

主题与 Button/Input/Select/Textarea 的基础映射已做源码检查及代表性浏览器试点；其他组件、完整状态组合和后端端到端仍需按任务验证。此前结果不能替代同步到新主分支后的检查。

按用户安排，新增 OpenSpec 业务流程试点暂缓，相关正式任务保持未完成；后续先准备交付分支、审阅与 CI。安装校验、正文送达、业务验收、远端 CI 和合并是分别记录的结果。本轮没有正式归档 OpenSpec 变更。
