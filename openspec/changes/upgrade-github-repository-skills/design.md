# Design

## Context

#1103 提供当前可用版本的完整清单。CLI 已有 `planSkillUpgrades`、`executeSkillUpgradePlan` 和安全本地 inventory；原版升级每次最多选择 50 个坐标。本实现作为 #1103 后的独立堆叠 PR，只增加仓库范围编排。

## Decisions

- 用服务器当前清单与指定 registry 下的本地 inventory 求交集，不爬取分页详情、不推测 Suite、也不只比较提交 SHA。
- 升级规划增加内部精确版本 resolver 与来源专属排序器注入，默认单技能升级仍使用既有 SemVer 行为。真实 GitHub 版本为 `0.0.0-g<内容摘要>-<ingestion后缀>`，哈希没有新旧顺序；仓库升级在同一 registry/namespace/slug、版本及指纹基线已核实的 metadata 中读取正整数 versionId，按同源版本创建序列判断，不将它误称为发布时间。精确版本/指纹相同时直接 unchanged；旧 metadata 缺可靠 versionId 且需要排序时保守 blocked，不做哈希排序回退或强制迁移。仓库编排将大选择分成不超过 50 个坐标的规划块，始终复用首次取得的固定版本清单，合并实际逐目标规划，不能重新解析 latest。
- 各技能 metadata 的可选 sourceRepositoryId 仅用于提示“曾来自本仓库、当前已不可用”的本地条目；更新资格仍以服务端清单为准。缺该提示的历史直接安装仍能按已验证的当前成员匹配。无法证明历史来源且当前也无法匹配时不猜测、不改文件。
- 需要更新的 disabled 目标在规划阶段即归入 blocked，不让可预知的原生事务限制变成执行失败。预期保护项保留为 blocked/not-attempted；从可执行集合排除后复用已有升级执行器。整体有保护项或失败时返回非零，同时准确保留独立成功项。执行器遇到意外失败仍沿用原有停止后续执行和逐目标回滚规则，不宣称跨文件系统事务。
- 不提供仓库批量 force。用户明确核查单个技能后仍可选择既有单技能升级能力。
- 网页安装面板只切换三种命令：安装、检查已安装更新、升级已安装技能。更新检查说明本地才知道安装情况，不增加远端安装状态 API 或“落后 N 项”徽标。

## Alternatives

将仓库自动创建 Suite 会改变领域语义和审核、版本关系，因此不采用。新建仓库安装账本能记成员历史，但当前逐技能 metadata 已能保存必要来源提示，额外状态和迁移成本不值得。仅逐个调用普通 upgrade 会在执行过程中重解析 latest，破坏本次固定版本，所以复用其规划和执行两段而非循环执行命令。

## Risks / Trade-offs

- 整个仓库清单不可读时无法安全匹配 → 请求失败且不写文件，不能由本地来源提示绕过权限。
- 旧 metadata 没有可靠来源 → 只处理当前已验证交集，其余留在本地，不编造归属。
- 规划后再次撤权、改文件或改 inventory → 原下载端、指纹及 CAS 再校验；执行失败结果保留。
- 部分更新成功意味着本地并非同一提交 → 这是独立技能的允许状态，输出具体版本，不加虚假的提交锁步约束。

## Migration Plan

无数据库或 inventory schema 迁移。升级 CLI 即可使用；旧 metadata 保持可读。回滚 CLI 不删除已安装文件。与 #1103 按顺序合入，分别保留验证范围与 PR。
