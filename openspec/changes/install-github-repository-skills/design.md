# Design

## Context

见 proposal.md。当前 catalog detail 优先选择完整可下载快照并分页；该查询不能作为日常批量安装清单。安装服务已有 `resolved` 输入、目标锁、CAS inventory、指纹和回滚，避免重写安装事务。

## Goals / Non-Goals

目标是增加仓库到精确技能版本的只读投影，CLI 编排独立安装，Web 帮助复制命令与核对版本。无需迁移，也不扩展审核、Suite 或快照状态机。#1110 的检查和升级单独处理。

## Decisions

1. 在 catalog query repository 复用当前可见性条件，新增与分页/快照无关的安装清单方法；单事务读取固定版本 ID、版本字符串、指纹。最多 1000 个可安装成员，超过上限明确拒绝，不能静默截断。相比逐页爬取详情，它避免漏成员和跨页版本漂移；相比持久化安装任务，它不引入不需要的数据库状态。
2. 提供 `/api/cli/v1/github-repositories/{repositoryId}/install-plan` 与 Web 等价入口，共享 DTO、查询与权限；Token 明确要求 `skill:read`，不自动增加审核或写入权限。下载继续调用现有带权限校验的版本下载路径。规划中的精确版本与下载内容通过指纹绑定。
3. CLI 新增 `repository install <repository-id>`，与 skill 坐标和 Suite 分开。稳定 ID 避免仓库改名后命令定位错误。计划一次获取并校验后顺序安装，传入现有 `resolved`，不再解析 latest；不开放批量 `--force`，避免一次覆盖大量本地修改。目标选择复用现有 Agent/目录/scope 行为。
4. 使用现有 inventory 表示每个技能及其目标；不增加仓库级安装记录。各技能 metadata 保存可选 sourceRepositoryId 来源提示，普通升级保留它；旧 metadata 缺字段仍可读取，该提示不授予任何权限。这取代旧 `add-github-repository-catalog/design.md` 中未来需要独立仓库安装记录的设想。#1110 用服务端真实绑定筛选可升级技能；来源提示只用来识别本仓库曾安装但当前不可用的本地项并提示保留，无需增加本地仓库账本。
5. Web 在既有仓库详情主操作增加安装按钮，使用已有 Button、复制能力和设计系统，以页内可收合面板呈现。内容说明为“各技能当前可用版本，可能来自不同提交”，并明确无已发布版本等成员不会被纳入；不展示无权限成员信息或推断本地状态。完整快照 ZIP 继续保留原有入口、全员可用条件和历史固定版本含义。

## Risks / Trade-offs

- 安装计划与下载之间可能撤权或撤回 → 现有下载端再次校验，CLI 逐项失败并返回非零，不宣称整体事务。
- 大仓库开销 → 确定上限并拒绝超限；后续如需扩大，另设计完整一致的分页协议。
- 混合版本容易被误认成仓库快照 → 入口、说明、命令、版本表明确区分。
- 不可访问/未发布内容可能泄漏 → 仅返回可分发成员，排除项使用通用说明，不返回隐藏数量或名称。
- 原客户端/服务端版本不匹配 → 新命令遇到缺失端点明确失败，原安装与快照功能不变。

## Migration Plan

无数据库变更。先升级服务端/Web，再分发 CLI。回滚本功能不删除现有逐技能安装记录或用户文件，旧 CLI 仍能读取已安装技能。
