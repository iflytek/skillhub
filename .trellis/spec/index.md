# SkillHub 工程规范索引

本目录是 SkillHub 工程约定的权威正文，随代码版本维护；不依赖工程 Skill 自动发现。
适用 AGENTS 指令仍优先。先选择领域，再读取触发条件对应的专题；不要默认加载整个目录。

## 按任务读取

| 任务 | 入口 | 条件性追加 |
|---|---|---|
| 页面、组件、状态、请求 | [前端](./frontend/index.md) | 公共接口变化追加后端 API 专题；动效读现有动效正文 |
| Java、接口、持久化、扫描集成 | [后端](./backend/index.md) | 按事务、错误、日志、扫描选专题，业务状态读正式契约 |
| 测试、CI、交付验收 | [测试](./testing/index.md) | 受影响领域的行为验收，跨域取并集 |
| 配置、镜像、发布、迁移 | [部署](./deployment/index.md) | 操作手册与环境检查；读取规范不是部署授权 |
| CLI | [CLI](./cli/index.md) | 后端 API 契约、测试、配置按实际影响追加 |
| 需求、开发、PR、收尾 | [工作流](./workflow/index.md) | 大型需求读 OpenSpec；已有任务收尾读归档 |
| 复用判断或跨层分析 | [思考指南](./guides/index.md) | 按问题选指南，不以问题清单替代契约 |

实现与检查使用相同的适用正文，检查可追加验收材料。目录存在、Skill可见、hook配置或链接有效，
分别不等于正文已读取、规则已执行或行为已验证。没有任务时直接读取，无需为加载规范创建任务。

读取与接续按[有界上下文读取](./workflow/context-reading.md)执行；避免合并大正文，截断后补读。

## 轻量使用方式

| 情况 | 使用方式 |
|---|---|
| 改文案、补规范或小修 | 读相关规则，直接修改验证，不强制建任务 |
| 多步功能 | 任务记录保存需求、上下文、进度、验证；尊重用户已有任务创建选择 |
| 大型需求或架构调整 | OpenSpec明确需求设计，Trellis组织执行与接续 |
| 已有权威文档 | 引用完整契约；关键规则可在 AGENTS 与专题重复，修改时检查一致性 |
| 换worktree | 从本机模板显式复用通用规则与工具配置，任务记录各自管理；已跟踪规范以分支内容为准 |

## 五类内容的职责

| 类型 | 应写什么 |
|---|---|
| 工程约定 | 范围、职责、模式、理由、例外 |
| 接口与行为契约 | 输入输出、成功失败、取消、并发、持久化及断言；具体产品语义引用正式来源 |
| 质量要求 | 改动触发条件、检查、可观察结果、证据限制 |
| 项目经验 | 真实触发、根因、预防和回归锚点；一次性过程留任务记录 |
| 思考指南 | 决策问题和规则链接，不暗中新增硬规则 |

五类是审查维度，不要求每篇填满，也不机械建立五套目录。
专题按独立适用条件拆分；详细契约有明确归属，关键规则可在 AGENTS 和专题重复，变更时一并核对，不能出现互相冲突的版本。
规则需有适用范围、例外和源码/测试/设计来源。
代码现状不自动等于正确标准：分别标明目标、已知偏差和已验证行为，冲突不能静默裁定。

## 正文应具体到什么程度

索引负责选择，思考指南可以提出问题；实现专题不能只写“注意兼容”“合理测试”“复用现有能力”。
对本次新增或调整的规则，评审时应能回答：

- **何时读：** 哪种改动触发它，哪些情况不适用？例如仅改翻译文字不等于修改请求行为。
- **改哪里：** 指向真实类、函数、配置字段或测试；命名只是建议时明确标注，不虚构已有 helper。
- **怎么做：** 给出本项目的代表例子，必要时附反例；不把第三方项目的框架和业务规则照搬过来。
- **怎样判定：** 指出输入与可观察结果，例如错误退出码、缓存是否清空、数据库是否回滚，而非只列测试命令。
- **哪些尚未做到：** 将现有行为、目标要求和缺口分开；已存在测试不等于本次已运行，计划中的断言不写成已有覆盖。

简单命名规则不必填五段模板，复杂专题也不靠凑示例数量证明完整。新增命令应说明工作目录、依赖和副作用。
规则变化同时核对 AGENTS 中的摘要、所属索引和专题；链接检查只能证明路径可达，内容仍需对照来源审查。

## 与其他资料的关系

- AGENTS直接保留关键产品、架构、安全与高频工程规则；本目录补充场景、例外、实现依据和验证方法。
- docs保留架构、业务语义和操作手册；OpenSpec保留正式需求、设计、行为变化与验收。
- POM、package.json、schema、源码、测试和脚本提供当前事实；规范链接它们，不维护重复版本清单。
- Trellis执行Skill只组织启动、读取、检查、收尾，不持有另一套项目规范。
- 学到经验时先判断是否稳定复用；需沉淀则更新所属专题及对应检查，不要求每次任务新增文档。

## 版本与本机模板

仅 `.trellis/spec/` 纳入Git；任务、journal、运行状态、个人配置和执行工具保持本地。
公开规范不能依赖私人绝对路径或未提交正文。新检出无需安装Trellis即可阅读本目录。
本机模板是显式复用与分发工具，不能静默覆盖当前分支已跟踪规范或同步其他worktree的任务。
本地同步/发布脚本存在时先核对实际范围、来源差异及备份；不因同步绕过AGENTS修改审批。
归档与清理按[任务记录](./workflow/task-archive.md)处理；无记录不强制创建。
