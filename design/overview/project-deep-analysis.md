# 项目深度分析

## 概览

SkillHub 当前是一个“技能注册中心 + 治理平台”项目，整体由 Java/Spring Boot 多模块后端、React/Vite 前端、以及一套文档站与设计/需求文档组成。

系统已经明显从“阶段性快速演进”进入“功能较完整但文档和历史资产需要收敛”的状态：

- 核心业务能力已经较全：
  - 技能发布、浏览、下载
  - 命名空间与治理
  - 审核、提升、举报
  - 收藏、评分、通知
  - 本地账号、OAuth、Device Auth、密码重置
  - 安全扫描与前端审核展示
- 运行时已经收敛为一条标准主线：
  - 标准 `MySQL 8 + Redis + local-file-index` 模式
- 仓库历史文档较多，包含大量阶段性计划、专题设计、一次性分析和已实现 PRD，适合进一步收敛。

## 后端架构

后端是 Maven 多模块工程，主模块边界如下：

- `skillhub-app`
  - Spring Boot 启动与控制器入口
  - 组装应用层配置、Flyway、Actuator、Web、限流、扫描接入
- `skillhub-domain`
  - 领域模型、领域服务、业务规则
  - 技能、命名空间、审核、提升、安全、标签等核心对象
- `skillhub-auth`
  - 认证授权、OAuth、本地账号、Device Auth、密码重置、会话能力
- `skillhub-infra`
  - JPA 仓储实现、WebClient/外部集成、持久化适配
- `skillhub-search`
  - 搜索实现
  - 当前以 `mysql + local-file-index` 为默认实现，保留 `mysql-like` 作为显式回退路径
- `skillhub-storage`
  - 存储 SPI 与本地/S3 适配
- `skillhub-notification`
  - 通知领域与基础能力

这个划分整体是合理的，优点是：

- 应用入口、领域规则、基础设施、搜索、存储被拆开
- 便于针对不同运行模式替换底层实现
- 本地轻量模式可在不推翻主链路的前提下逐步引入

当前的主要结构问题不在“模块是否存在”，而在“历史演进造成的边界轻微重叠”：

- `app/domain/infra` 的职责局部仍有交叉
- 一些功能是按增量演进叠上去的，导致配置和适配逻辑分散
- 运行时从 PostgreSQL 迁移到 MySQL 后，历史文档、测试口径和少量命名残留仍需持续收口

## 前端架构

前端基于 React + Vite + TanStack Router/Query，结构以功能域组织为主：

- `web/src/features/*`
  - 按领域拆分功能模块，如 `auth`, `search`, `review`, `skill`, `security-audit`, `namespace`
- `web/src/pages/*`
  - 页面层，包括普通页、dashboard、admin、settings
- `web/src/shared/*`
  - UI 组件、hooks、工具函数
- `web/src/api/*`
  - API client 与生成类型

前端的成熟度已经不低，能看出以下特点：

- 页面和 feature 的分工较明确
- 审核、安全、文件预览、详情页等复杂交互已经具备独立 feature
- 类型生成链路已经进入仓库

主要问题在于：

- 历史专题功能增加较多后，`shared` 与 `features` 的边界仍需持续收口
- 文档里记录过的部分结构问题在代码里已经改善，但文档层没有同步收敛

## 运行模式与基础设施

当前项目实际以 MySQL 路径作为正式源码运行模式：

### 1. 标准模式（当前主路径）

- 数据库：MySQL 8
- 缓存/会话：Redis
- 搜索：`local-file-index`（Lucene）
- Flyway：开启
- 目标：尽量贴近真实生产行为

历史材料中出现的 `local-h2` / `h2-like` 仅代表过渡阶段背景，不再属于当前正式源码运行路径。

优点：

- 减少本地环境依赖
- 便于前后端联调
- 为未来数据库可插拔方向保留过渡期经验

风险：

- 数据库迁移策略、文档与脚本如果继续叠加，会加重维护负担

## 数据、搜索、认证、治理

### 数据层

当前主数据模型已经覆盖：

- 用户/身份绑定/角色权限
- 命名空间/成员关系
- 技能/版本/文件/标签
- 审核/提升/举报
- 收藏/评分
- 通知/通知偏好
- 安全审计

这套模型已经偏平台化，不再是单一 CRUD 应用。

### 搜索

搜索是当前系统里最值得单独维护边界的能力：

- `local-file-index` 承担当前主搜索能力
- `mysql-like` 是显式回退实现
- 这意味着搜索不再只是一个查询接口，而是“有引擎差异的子系统”。  
后续如果继续扩展搜索能力，Lucene 文档模型、重建流程和数据库权威快照的一致性会是首要边界。

### 认证

认证体系复杂度已经明显提高：

- OAuth2
- 本地账号
- 会话 bootstrap
- Device Auth
- 密码重置
- 多账号合并

这部分能力已经足以支撑多入口平台，但也意味着：

- 配置项较多
- 文档必须保持清晰，否则接入成本会上升

### 治理

治理链路已经非常完整：

- namespace 生命周期治理
- skill 审核、提升、隐藏/撤回
- 安全扫描与审核展示
- 审计与通知

这使项目明显具备“平台治理后台”属性，而不是单纯的技能市场。

## 主要风险

### 1. 运行模式文档与实际代码分叉

`local-h2`、Flyway 收敛、Redis 剪裁、搜索双实现这些能力已经进入代码，但文档仍有历史叠层，容易误导维护者。

### 2. 文档入口过多

`docs/`、`docs/prds/`、`design/`、`design/implemented/` 多层并存后，如果没有明确分工，新增文档还会继续扩散。

### 3. 历史计划与当前实现混杂

过去的阶段计划、注释分析、专题设计在历史上有价值，但继续留在主路径会降低当前文档信噪比。

### 4. 文档与历史材料收敛风险

MySQL 运行时已经落地，但不少设计材料仍带着 PostgreSQL 时代的前提；如果不在设计层明确“现状”和“历史背景”的边界，后续维护者仍可能被旧材料带偏。

## 建议沉淀的设计文档

当前最值得长期保留在 `design/` 下的文档类型是：

1. 项目总览与模块边界
2. 运行模式与环境矩阵
3. 文档治理规则
4. 数据库初始化/重置策略
5. 已实现需求归档

这几类文档比阶段计划更有长期价值，也更适合作为未来维护入口。
