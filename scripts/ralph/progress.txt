## Codebase Patterns
- New auth-provider integrations should normalize upstream provider payloads into small internal DTO/record types inside `skillhub-auth`, so application services never depend on provider-specific contracts.
- When running Maven from `server/pom.xml` with `-pl ... -am -Dtest=...`, add `-Dsurefire.failIfNoSpecifiedTests=false` so upstream modules without matching tests do not fail the build.
- Optional Redis-backed auth helpers in this codebase should choose Redis vs local fallback in a dedicated `@Configuration` bean via `ObjectProvider<RedisTemplate<...>>`, not by scattering cache-mode branches through services.
- Configuration-only behavior here is usually validated with lightweight `Binder` or `ApplicationContextRunner` tests instead of full `@SpringBootTest` contexts.
- Browser login flows here should reuse `OAuthLoginRedirectSupport` for `returnTo` sanitization and default target handling, instead of duplicating redirect validation rules in each auth provider.
- New enterprise auth providers should map a stable upstream identifier into `IdentityBinding.subject` and delegate local user creation through `IdentityBindingService`, rather than introducing fallback matching by display name or email.
- Spring beans in this codebase that keep an extra test-only constructor should mark the production constructor explicitly (for example with `@Autowired`), otherwise enabling the bean can fail with `No default constructor found`.
- Conditional auth endpoints that depend on provider beans need a local/mock provider implementation for runtime/OpenAPI verification; otherwise code can compile and tests can pass while the real app still exposes 404s for the new routes.
